# ファイル権限と特殊権限

Linux セキュリティの第一歩は **ファイル権限** です。このモジュールでは基本権限(rwx)と umask、setgid や sticky bit のような特殊権限、ACL による細かなアクセス制御、そして実際のシステムで危険な権限を見つけて直す監査までを扱います。

現在のユーザーを確認してみましょう。`learner` は sudo が使える一般ユーザーです。

```
id
```

- `id` — 現在のユーザーの UID、プライマリグループ(`gid`)、所属するすべてのグループ(`groups`)を表示する。

権限の表記は 2 通りを行き来できる必要があります。

| 表記 | 例 | 意味 |
|---|---|---|
| シンボリック | `rwxr-x---` | 所有者 rwx / グループ r-x / その他なし |
| 8 進数 | `750` | r=4, w=2, x=1 の合計 |

## 基本権限と umask

ファイルを作るときのデフォルト権限は **umask** が決めます。

現在の umask の値を確認:

```
umask
```

- `umask` — 新しいファイル/ディレクトリから **取り除く** 権限ビット。よくある `0022` はグループ・その他の書き込み(w)を外す → ファイル 644、ディレクトリ 755。

ファイルを 1 つ作り、実際にどんな権限でできるかを確認:

```
touch /tmp/t1 && stat -c %a /tmp/t1
```

- `touch` — 空のファイルを作る(あれば更新時刻だけ変える)。`&&` — 前のコマンドが成功したら続けて実行。
- `stat -c %a` — 書式指定(`-c`)で権限を 8 進数(`%a`)だけ表示する。

次に自分だけがアクセスできる作業スペースを作ります。要件:

- `~/work` ディレクトリ — 権限 **700**(所有者だけ rwx)
- `~/work/secret.txt` ファイル — 内容は自由、権限 **600**(所有者だけ rw)

作業ディレクトリを作って 700 に:

```
mkdir -p ~/work && chmod 700 ~/work
```

- `mkdir -p` — 上位のパスまで作り、すでにあってもエラーにしない。
- `chmod 700` — 8 進数で権限を指定: 所有者 rwx(7)、グループ・その他なし(0)。

秘密ファイルの作成:

```
echo "top secret" > ~/work/secret.txt
```

- `echo "…" > ファイル` — 文字列をファイルに書く(なければ作成、あれば上書き)。新しいファイルの権限は umask に従う。

ファイルの権限を 600 に:

```
chmod 600 ~/work/secret.txt
```

- `600` — 所有者 rw(6 = 4+2)、グループ・その他なし。シンボリックでは `chmod u=rw,go= <ファイル>`。

`stat` で確認して **[チェック]** してください。

```
stat -c '%a %n' ~/work ~/work/secret.txt
```

- `%a` は 8 進数の権限、`%n` はファイル名。ファイルを複数渡すと 1 行ずつ表示する。

> ディレクトリの `x` は「通過(進入)権限」です。ディレクトリに `r` があっても `x` がなければ中のファイルにアクセスできません — ステップ 3 の ACL で再び出てきます。

## setgid と sticky bit

チーム共有ディレクトリを作るときによく使う特殊権限 2 つ:

| ビット | 8 進数 | ディレクトリでの効果 |
|---|---|---|
| setgid | 2000 | 中に作られるファイルが **ディレクトリのグループを継承** |
| sticky | 1000 | ファイルの削除は **所有者だけ** が可能(`/tmp` と同じ方式) |

`share` グループの共有ディレクトリ `/srv/share` を作ってください。要件:

- グループ作成: `share`
- `/srv/share` ディレクトリ、所有グループ `share`
- 権限 **3775** = setgid(2000) + sticky(1000) + 775

グループの作成:

```
sudo groupadd -f share
```

- `groupadd` — グループを作る。`-f` はすでにあってもエラーにせず成功で終わる。

共有ディレクトリの作成:

```
sudo mkdir -p /srv/share
```

- `/srv` は root 所有なので `sudo` で作る。

所有グループを share に:

```
sudo chgrp share /srv/share
```

- `chgrp <グループ> <パス>` — 所有グループだけを変える。所有者も変えるなら `chown ユーザー:グループ`。

特殊権限を含めて 3775 に:

```
sudo chmod 3775 /srv/share
```

- 4 桁の 8 進数の先頭桁が特殊ビット: `3` = setgid(2)+ sticky(1)。残りの `775` は所有者・グループ rwx、その他 r-x。

結果を確認しましょう。シンボリック表記では setgid はグループの位置の `s`、sticky は最後の位置の `t` として表れます(`drwxrwsr-t`)。

権限と所有グループの確認:

```
stat -c '%a %G %n' /srv/share
```

- `%G` — 所有グループの名前。

シンボリック表記の確認:

```
ls -ld /srv/share
```

- `ls -ld` — 中身ではなくディレクトリ **そのもの**(`-d`)をシンボリック表記(`drwxrwsr-t`)で表示する。

確認できたら **[チェック]** してください。

## ACL による細かなアクセス制御

`rwx` には所有者/グループ/その他の 3 枠しかありません。「このファイルを **特定のユーザー 1 人** にだけ読ませる」は **ACL**(Access Control List)で解決します。

システムには監査担当のアカウント `audit` が用意されています。ステップ 1 で作った `~/work/secret.txt` を audit に **読み取り専用** で開放してください。

audit に読み取り ACL を付与:

```
setfacl -m u:audit:r ~/work/secret.txt
```

- `setfacl -m` — ACL の項目を追加/変更(modify)する。形式は `u:<ユーザー>:<権限>`(グループは `g:`)。

付いた ACL の確認:

```
getfacl ~/work/secret.txt
```

- `getfacl` — ファイルの所有者・グループ・ACL の全項目と `mask`(ACL の最大許可値)を表示する。

ところがこれで終わりではありません — audit がファイルまで **たどり着く** には、パス上のディレクトリ(`~` と `~/work`)を通過できなければなりません。700 のディレクトリは audit をはじきます。

通過(x)権限だけを ACL で開放:

```
setfacl -m u:audit:x ~ ~/work
```

- ディレクトリに `x` だけを与えると、一覧表示(r)なしで **通過** だけを許す。2 つのパス(`~`、`~/work`)に一度に適用する。

audit の立場で実際にできるか検証しましょう。

読み取り — 成功するはずです:

```
sudo -u audit cat ~/work/secret.txt
```

- `sudo -u <ユーザー> <コマンド>` — 別のユーザーとしてコマンドを実行し、実際の権限を検証する。

書き込み — 失敗するはずです:

```
sudo -u audit sh -c 'echo x >> ~learner/work/secret.txt'
```

- `sh -c '…'` — リダイレクト(`>>`)まで audit の権限で実行されるよう、シェルごと audit として起動する。
- `~learner` — learner ユーザーのホームディレクトリ(audit から見ると `~` は自分のホームなので)。

ACL が付いたファイルは `ls -l` で権限の後ろに `+` が付きます。確認したら **[チェック]** してください。

## 権限の監査と修理

最後は実務的な課題です。**SUID**(4000)ビットが付いた実行ファイルは所有者(たいてい root)の権限で実行されるので、監査対象の筆頭です。

システム全体から SUID ファイルを探して保存:

```
sudo find / -xdev -perm -4000 -type f > ~/work/suid.txt
```

- `find /` — ルートから再帰的に探す。`-xdev` — ほかのファイルシステム(/proc など)には入らない。
- `-perm -4000` — SUID ビットを **含む** ファイル(`-` は「これらのビットをすべて持つ」)。`-type f` — 通常ファイルだけ。
- `> ~/work/suid.txt` — 結果の一覧をファイルに保存する。

一覧の確認:

```
cat ~/work/suid.txt
```

- `cat` — 保存した SUID ファイルの一覧を表示する。

`passwd` がなぜ SUID なのか考えてみましょう — 一般ユーザーが root 所有の `/etc/shadow` を更新する必要があるからです。

2 つ目の課題: `/opt/lab/perm/danger.conf` は DB のパスワードが入った設定ファイルなのに、権限が **666**(誰でも読み書き可能!)で配布されています。

現在の権限の確認:

```
ls -l /opt/lab/perm/
```

- `ls -l` — 権限(`-rw-rw-rw-` = 666)と所有者・グループを確認する。

640 に修理:

```
sudo chmod 640 /opt/lab/perm/danger.conf
```

- `640` — 所有者 rw、グループ r、その他なし。アプリはグループ権限で読めるように残し、それ以外は塞ぐ。

修理したら **[チェック]** でモジュール完了です。
