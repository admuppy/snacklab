# 総合 — 停止したサービスを復旧する

午前 2 時、アラートが鳴ります: **「lab-app が起動しません。」** このモジュールは、これまで学んだすべて(systemd、journald、シグナル・ポートの追跡、ファイル権限)を総動員して、実際の障害を最初から最後まで収拾する総合シナリオです。

今回はコマンドをいちいち教えません — **診断の順序** がこのモジュールの学習目標です。行き詰まったら以前のモジュールのツールを思い出してください: `systemctl status/cat`、`journalctl -u`、`sudo ss -ltnp`、`ls -l`、`sudo -u <ユーザー>`。

まず現状を把握しましょう。

```
systemctl status lab-app --no-pager
```

- `Active:` の行(状態)と最後のログ数行から最初の手がかりを探す。`--no-pager` は less を通さずそのまま表示。

## 起動失敗の診断 — 203/EXEC

status だけで足りなければ、journal が答えを知っています。

```
journalctl -u lab-app --no-pager | tail -20
```

- `journalctl -u <ユニット>` — そのユニットのログだけ。`| tail -20` で最新の 20 行に集中する。

`status=203/EXEC` — linux-06 で出会ったあのコードです。ユニットが **何を実行しようとして** 失敗したのかを確認してください。

```
systemctl cat lab-app
```

- ユニットファイルの内容をそのまま見る。`ExecStart=`(何を実行するか)と `User=`(誰として実行するか)に注目しよう。

ExecStart のインタープリターのパスが、このシステムに実際に存在するかを突き合わせてみてください(`ls /usr/bin/python3*`)。存在しないバージョンを指しているはずです — デプロイスクリプトが別のサーバーを基準に書かれていた、よくある事故です。

課題: ExecStart を実在するインタープリターに直して `daemon-reload` してください。直したら **[チェック]**。

> まだ start は成功しません — 障害はたいてい 1 層ではありません。次のステップへ。

## ポート競合の解決

今度は start すると別のエラーが出ます。

サービスの起動を試す:

```
sudo systemctl start lab-app
```

- 修理後にもう一度起動してみる。失敗すれば、次のログが新しい原因を教えてくれる。

エラーログの確認:

```
journalctl -u lab-app --no-pager | tail -5
```

- 今回の試行のログだけを見ればよいので最後の 5 行。

`Address already in use` — lab-app が使う 8080 を **誰かが先に取っています**。linux-02・07 で学んだポートの追跡で犯人を探してください。

```
sudo ss -ltnp | grep 8080
```

- 8080 でリッスンしているソケットとそのプロセス(`users:(("名前",pid=…))`)を探す。PID を覚えておこう。

PID からユニットを逆引きするには `systemctl status <PID>` が便利です。犯人は廃止予定のレガシーユニットです。停止するだけでは再起動時に復活するので、**disable まで** する必要があります。

課題: 先取りしているユニットを `disable --now` で落とし、lab-app を起動してください。lab-app が active になったら **[チェック]**。

## 権限の問題の解決

サービスは起動しましたが……まだ終わりではありません。

```
curl -i http://127.0.0.1:8080/index.html
```

- `curl -i` — レスポンス本文の前に、ステータス行(`HTTP/1.0 404 …`)とヘッダーも一緒に(include)表示する。

**404** — でもファイルは確かにあります(`ls -l /srv/lab-app/`)。なぜでしょう?

手がかりは 2 つです。① ユニットに `User=labapp` があります — サービスは root ではなく labapp として動きます。② index.html は `root:root 600` — **labapp は読めません。** このサーバー(http.server)はファイルを開けないと 404 を返します。「ファイルがあるのに 404」の典型的な権限の問題です。

疑いを検証する習慣 — そのユーザーの立場で直接読んでみましょう。

```
sudo -u labapp cat /srv/lab-app/index.html
```

- `sudo -u <ユーザー> <コマンド>` — そのユーザーの権限でコマンドを実行する。サービスが見ているのと同じ権限でファイルを読んでみる検証方法。

課題: labapp が読めるように所有権または権限を直してください(linux-01 の感覚で — 必要以上に開けないこと)。curl が `LAB APP OK` を返したら **[チェック]**。

## 再発防止と仕上げ

復旧は「今動くようにする」+ **「次も動くようにする」** までが 1 セットです。チェックリスト:

1. lab-app は **enable** 状態か?(再起動するとまた死ぬ復旧は復旧ではありません)
2. 最終的な応答を証拠として残す — `~/work/final.txt` に保存

起動時の自動開始を登録:

```
sudo systemctl enable lab-app
```

- `enable` — 起動時の自動開始を登録する(シンボリックリンクを作成)。今動いているサービスには影響しない。`systemctl is-enabled lab-app` で確認できる。

最終的な応答を保存:

```
curl -s http://127.0.0.1:8080/index.html > ~/work/final.txt
```

- `curl -s` で受け取ったレスポンス本文を `>` でファイルに保存する。

保存内容の確認:

```
cat ~/work/final.txt
```

- 保存した応答が `LAB APP OK` かを確認する。

**[チェック]** すれば Linux トラック完走です。今日収拾した 3 重の障害(間違ったパス → ポート競合 → 権限)は実際の障害報告で最もよくある組み合わせだということ、そしてその 3 つとも **journal と ss と ls -l が先に知っていた** ことを覚えておいてください。
