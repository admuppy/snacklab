# ネットワーク診断

「サービスにつながりません」の原因はたいてい 4 つのうちのどれかです — **IP が違う、ポートが開いていない、バインドが間違っている、名前が解決できない。** このモジュールでは、その 4 つを順番に診断するツール(ip、ss、curl、getent)を身につけます。

実習環境には `lab-api` という API サービスが動いています — ところが「外から接続できない」という報告が上がっている状態です。最後まで進めば原因を見つけて直すことになります。

## インターフェースと IP の調査

ネットワーク診断の出発点は **自分が誰か**(IP)を確認することです。今の標準ツールは `ip` です(ifconfig は引退しました)。

インターフェース一覧の確認:

```
ip link
```

- `ip link` — ネットワークインターフェース(L2)の一覧と状態(`UP`/`DOWN`)、MAC アドレス、MTU を表示する。

IPv4 アドレスの確認:

```
ip -4 addr show
```

- `ip addr show` — インターフェースごとの IP アドレス。`-4` で IPv4 だけ。`inet 10.x.x.x/24` のようにアドレス/プレフィックス長(CIDR)で表示される。

ルーティングテーブルの確認:

```
ip route
```

- `ip route` — ルーティングテーブル。`default via <ゲートウェイ>` の行が外へ出るデフォルトの経路。

コンテナには普通 `lo`(ループバック)と `eth0` の 2 つが見えます。スクリプトで使いやすい 1 行での取り出し方:

eth0 を 1 行で表示:

```
ip -4 -o addr show eth0
```

- `-o` — 1 つのインターフェースの情報を **1 行**(oneline)で。`grep`・`awk` で加工しやすい。
- `show eth0` — 特定のインターフェースだけ。

CIDR のフィールドだけを取り出す:

```
ip -4 -o addr show eth0 | awk '{print $4}'
```

- `awk '{print $4}'` — 空白区切りの 4 番目のフィールド(`10.x.x.x/24`)だけを取り出す。

課題: eth0 の IPv4 アドレスを **CIDR なしのアドレスだけ** で `~/work/myip.txt` に保存してください。`/24` のようなサフィックスは `cut -d/ -f1` で取り除きます。

アドレスだけを取り出して保存:

```
ip -4 -o addr show eth0 | awk '{print $4}' | cut -d/ -f1 > ~/work/myip.txt
```

- `cut -d/ -f1` — `/` を区切り文字(`-d`)にして切り、最初のフィールド(`-f1`)だけ → アドレスの部分。
- `> ~/work/myip.txt` — 結果をファイルに保存する。

保存内容の確認:

```
cat ~/work/myip.txt
```

- 保存したアドレスを表示して確認する。以降のコマンドで `$(cat ~/work/myip.txt)` として再利用する。

保存したら **[チェック]** してください。

## リッスン中のソケットの追跡

次の問い: **何がどのポートで待ち受けているか。** `ss` の必須の組み合わせから。

| オプション | 意味 |
|---|---|
| `-l` | リッスン中のソケットだけ |
| `-t` / `-u` | TCP / UDP |
| `-n` | ポートを数字で(サービス名への変換を省略) |
| `-p` | プロセスを表示(他人のものは sudo が必要) |

```
sudo ss -ltnp
```

- 上の表のオプションの組み合わせ。結果の `Local Address:Port` がどのアドレス・ポートで待ち受けているかを、`users:((…))` がどのプロセスかを教えてくれる。

課題: `lab-api.service` がリッスンしている **ポート番号** を探して `~/work/api-port.txt` に保存してください。ユニットのメイン PID から出発するのも良いルートです。

lab-api のメイン PID の確認:

```
systemctl show -p MainPID --value lab-api
```

- `systemctl show -p MainPID --value <ユニット>` — ユニットのメインプロセスの PID の値だけを表示する。

その PID のリッスン中ソケットを探す:

```
sudo ss -ltnp | grep "pid=$(systemctl show -p MainPID --value lab-api)"
```

- ダブルクォートの中の `$( … )` も置換される → `grep "pid=1234"` となり、その PID のソケットの行だけが残る。

Local Address 列の `127.0.0.1:ポート` からポートだけを読めば OK です。保存したら **[チェック]** してください。

## バインドの問題の診断と修理

さきほどの ss の出力で気づいたかもしれません — lab-api の Local Address が `127.0.0.1:9090` です。**ループバックにだけバインド** されているので、このコンテナの中では使えても、外(ほかの Pod、ノード)からは connection refused になるのです。再現してみましょう。

ループバックで接続:

```
curl -s http://127.0.0.1:9090/status.json        # 成功
```

- `curl -s <URL>` — 静かにリクエストし、レスポンス本文だけを表示する。ループバック(`127.0.0.1`)ではつながる。

コンテナの IP で接続:

```
curl -s --max-time 3 http://$(cat ~/work/myip.txt):9090/status.json   # 失敗!
```

- `--max-time 3` — リクエスト全体を 3 秒に制限する(応答がなければ待たない)。
- `$(cat ~/work/myip.txt)` — 保存しておいたコンテナの IP を URL に埋め込む。

同じプロセスなのに、**どのアドレスから入ってくるか** で結果が違います。`0.0.0.0`(すべてのインターフェース)にバインドを変える必要があります。

課題: ユニットファイルの `--bind 127.0.0.1` を `--bind 0.0.0.0` に直して再起動してください。

ユニットファイルの修正:

```
sudo vim /etc/systemd/system/lab-api.service
```

- `ExecStart=` の行の `--bind 127.0.0.1` を探して直す。vim: `i` で入力、`Esc` → `:wq` で保存・終了。

変更の再読み込み:

```
sudo systemctl daemon-reload
```

- ユニットファイルを直したので、systemd に読み直させる。

サービスの再起動:

```
sudo systemctl restart lab-api
```

- 新しいバインドアドレスでプロセスを立ち上げ直す。

バインドアドレスの確認:

```
sudo ss -ltn | grep 9090
```

- プロセス名は不要なので `-p` なしで。`0.0.0.0:9090` ならすべてのインターフェースで受け付ける。

コンテナの IP で再接続:

```
curl -s http://$(cat ~/work/myip.txt):9090/status.json   # 今度は成功
```

- 同じリクエストをもう一度送り、今度は応答が来るかを確認する。

`0.0.0.0:9090` に変わり、コンテナの IP で応答すれば **[チェック]** してください。

## 名前解決 — hosts と DNS

最後のピースは **名前 → IP** です。解決の順序はふつう `/etc/hosts` → DNS(`/etc/resolv.conf` のネームサーバー)で、その順序のルールは `/etc/nsswitch.conf` の `hosts:` 行が決めています。

DNS サーバーの設定の確認:

```
cat /etc/resolv.conf
```

- `nameserver` — 問い合わせる DNS サーバー、`search` — 短い名前の後ろに順に付けて試すドメインの一覧。

解決順序のルールの確認:

```
grep hosts /etc/nsswitch.conf
```

- `hosts: files dns` — まず `files`(=`/etc/hosts`)、なければ `dns` の順で名前を解決するという意味。

参照ツールは用途が違います: `nslookup`/`dig` は **DNS サーバーに直接** 聞き、`getent hosts` は **システムの実際の解決経路**(hosts ファイルを含む)をたどります。アプリケーションが見る結果は getent の方です。

課題: `api.lab.local` という名前で lab-api にアクセスできるようにしてください。DNS サーバーは直せないので `/etc/hosts` に登録します。

hosts ファイルに名前を登録:

```
echo '127.0.0.1 api.lab.local' | sudo tee -a /etc/hosts
```

- `tee -a` — ファイルを上書きせず末尾に **追加**(append)する。付け忘れると hosts ファイル全体が 1 行になってしまう!
- 形式: `<IP> <名前> [別名…]`。

システムの解決経路で参照:

```
getent hosts api.lab.local
```

- `getent hosts <名前>` — nsswitch の順序どおりに(hosts ファイルを含めて)名前を解決する。アプリケーションが見る結果と同じ。

名前で接続:

```
curl -s http://api.lab.local:9090/status.json
```

- IP の代わりに名前でリクエストする。curl もシステムのリゾルバーを使うので `/etc/hosts` の項目が適用される。

応答が来たら **[チェック]** — モジュール完了です。
