# プロセスとシグナル

サーバーが遅い・おかしいときに真っ先にやることは **プロセスをのぞくこと** です。このモジュールでは ps と /proc でプロセスを調べ、シグナルで制御し、ターミナルから切り離したバックグラウンド実行を作り、ポートを占有しているプロセスを突き止めます。

実習環境には 3 つのデーモンが systemd ユニットとしてあらかじめ動いています。

| プロセス | 正体 |
|---|---|
| `lab-worker` | 普通のワーカー — ステップ 1 の調査対象 |
| `lab-stubborn` | **SIGTERM を無視する** ゾンビのようなやつ — ステップ 2 で退治 |
| `lab-listener` | 127.0.0.1:5555 を占有している何か — ステップ 4 で追跡 |

## プロセスの調査 — ps と /proc

まず全プロセスをざっと見ます。

全体一覧をざっと見る:

```
ps aux | head
```

- `ps aux` — すべてのユーザー(`a`、`x`: ターミナルのないものも含む)のプロセスを、ユーザー・CPU%・MEM%・コマンドとともに(`u`)表示する。
- `| head` — 先頭 10 行だけを見る。

ツリー形式で見る:

```
ps -ef --forest | head -30
```

- `ps -ef` — すべてのプロセス(`-e`)を PID・PPID を含む完全形式(`-f`)で。
- `--forest` — 親子関係をインデントしたツリーで描く。`head -30` で先頭 30 行だけ。

`lab-worker` を探しましょう。`pgrep -f` はコマンドライン全体からパターンを探して PID を返します。

```
pgrep -f /opt/lab/bin/lab-worker
```

- `pgrep <パターン>` — 名前がパターンに合うプロセスの PID だけを表示する。
- `-f` — プロセス名ではなく **コマンドライン全体**(パス・引数を含む)から探す。

ps が表示するすべての情報の出どころは **/proc ファイルシステム** です。PID ディレクトリの中を直接見てみましょう(cmdline は NUL(\0)で区切られているので tr で置き換えて読みます)。

PID を変数に保存:

```
pid=$(pgrep -f /opt/lab/bin/lab-worker | head -1)
```

- `$( ... )` — コマンド置換。出力(PID)をシェル変数 `pid` に入れる。以降は `$pid` で使う。
- `| head -1` — 複数見つかっても最初の PID 1 つだけ。

PID ディレクトリの中身を確認:

```
ls /proc/$pid/
```

- `/proc/<PID>/` — カーネルがプロセス情報をファイルのように見せる仮想ディレクトリ。`cmdline`(実行時の引数)、`status`(状態・メモリ)、`fd/`(開いているファイル)、`environ`(環境変数)などがある。

cmdline を読む:

```
tr '\0' ' ' < /proc/$pid/cmdline; echo
```

- `tr '\0' ' '` — 入力の NUL 文字を空白に置き換える(translate)。
- `< ファイル` — ファイルを標準入力に流し込む。`; echo` は最後に改行を足す。

課題: 結果をファイルに保存してください。

- `~/work/worker.pid` — lab-worker の PID
- `~/work/worker.cmdline` — `/proc/<PID>/cmdline` の内容(tr で変換したもの)

作業ディレクトリの作成:

```
mkdir -p ~/work
```

- `mkdir -p` — 必要な上位ディレクトリまで作り、すでにあってもエラーにしない。

PID の保存:

```
echo "$pid" > ~/work/worker.pid
```

- `echo "$pid"` — 変数の値を出力する。`> ファイル` でその出力をファイルに保存(上書き)する。

cmdline の保存:

```
tr '\0' ' ' < /proc/$pid/cmdline > ~/work/worker.cmdline
```

- さきほど画面に出した `tr` コマンドと同じ。今度は結果を `>` でファイルに保存する。

保存したら **[チェック]** してください。

## シグナルでプロセスを制御する

`kill` はプロセスを殺すコマンドではなく、**シグナルを送る** コマンドです。

| シグナル | 番号 | 特徴 |
|---|---|---|
| SIGTERM | 15 | デフォルト。プロセスが **無視したり、後片付けしてから終了したりできる** |
| SIGKILL | 9 | カーネルが即座に除去。**無視できず**、後片付けの機会もない |
| SIGHUP | 1 | 慣例的に「設定の再読み込み」によく使われる |

`lab-stubborn` は TERM と INT を trap で無視するように作られています。確かめてみましょう。

生きているか確認:

```
pgrep -f /opt/lab/bin/lab-stubborn
```

- PID が表示されれば生きている。何も出なければ(終了コード 1)そのプロセスは存在しない。

SIGTERM を送る:

```
sudo pkill -TERM -f /opt/lab/bin/lab-stubborn
```

- `pkill` — パターンに合うプロセスにシグナルを送る(`pgrep` + `kill`)。
- `-TERM` — 送るシグナル(SIGTERM、15)。`-f` でコマンドライン全体から探す。
- `sudo` — 別のユーザー(root)が起動したプロセスなので管理者権限が必要。

まだ生きているか確認:

```
sleep 1; pgrep -f /opt/lab/bin/lab-stubborn   # まだ生きている
```

- `sleep 1` — 1 秒待つ。シグナル処理の時間を与えてから `;` で続けて再確認する。

注意点: このプロセスは **systemd ユニット**(lab-stubborn.service)が管理しています。プロセスだけを kill -9 してもよいのですが、ユニットで管理されているプロセスはユニットのレベルで扱うのが定石です。ただし `systemctl stop` はまず TERM を送ってタイムアウト(デフォルト 90 秒)まで待つので、こいつには遅すぎます — **ユニット経由で SIGKILL を直接送る** 方法を使ってください。

ユニット経由で SIGKILL を送る:

```
sudo systemctl kill -s KILL lab-stubborn
```

- `systemctl kill <ユニット>` — ユニットに属する **すべてのプロセス** にシグナルを送る。
- `-s KILL` — 送るシグナルを SIGKILL(9)に。プロセスが横取りできないので即座に除去される。

終了の確認:

```
pgrep -f /opt/lab/bin/lab-stubborn || echo "terminated"
```

- `A || B` — A が失敗(終了コード ≠ 0)したときだけ B を実行する。`pgrep` が何も見つけなければメッセージが出る。

死んだら **[チェック]** してください。

## セッションから切り離したバックグラウンド実行

ターミナルで `&` を付けて起動したプロセスは、ターミナルが切れると SIGHUP を受けて一緒に死にます。セッションが終わっても生き残らせるには **nohup**(HUP を無視 + 出力をリダイレクト)や **setsid**(新しいセッションに切り離す)を使います。

`/opt/lab/bin/lab-batch` は、最初の引数で受け取ったファイルに 10 秒ごとにタイムスタンプを書くバッチです。これをターミナルから切り離して起動し、ログは `~/work/batch.log` に送ってください。

```
nohup /opt/lab/bin/lab-batch ~/work/batch.log >/dev/null 2>&1 &
```

- `nohup <コマンド>` — SIGHUP を無視させ、ターミナルが閉じても動き続けるようにする。
- `>/dev/null 2>&1` — 標準出力を捨て、標準エラー(2)も標準出力(1)と同じところへ送る。
- 末尾の `&` — バックグラウンドで実行し、すぐにプロンプトを返す。

親プロセスを確認してみましょう。シェルから切り離されて孤児になると、PID 1(Pod では systemd)が引き取ります。

```
ps -o pid,ppid,cmd -p $(pgrep -f /opt/lab/bin/lab-batch)
```

- `ps -o pid,ppid,cmd` — 表示する列を PID・親 PID・コマンドに指定する。
- `-p $(pgrep ...)` — コマンド置換で得た PID のプロセスだけを参照する。

ログの確認:

```
tail ~/work/batch.log
```

- `tail <ファイル>` — ファイルの末尾 10 行。追いかけながら見るなら `tail -f`(Ctrl+C で終了)。

PPID が 1 でログが溜まっていれば **[チェック]** してください。

> 実務ではこうした一時的なデーモンより systemd ユニット(または `systemd-run`)が正解です — linux-06 モジュールで扱います。

## ポートを占有するプロセスの追跡

「このポート誰が握ってるの?」は最もよくある診断の質問です。`ss`(socket statistics)で 5555 番ポートの持ち主を探してみましょう。プロセス名を見るには `-p` が必要で、他人のプロセスは sudo がないと見えません。

リッスン中のソケットをすべて見る:

```
sudo ss -ltnp
```

- `ss` — ソケットの状態を参照する(netstat の後継)。`-l` リッスン中のソケットだけ、`-t` TCP、`-n` ポートを名前でなく数字で、`-p` ソケットを開いたプロセスまで表示。

5555 番ポートだけを参照:

```
sudo ss -ltnp sport = :5555
```

- `sport = :5555` — フィルター式。送信元(ローカル)ポートが 5555 のソケットだけを表示する。

`lsof` でも同じ答えが得られます。

```
sudo lsof -i :5555
```

- `lsof` — 開いているファイルの一覧(Linux ではソケットもファイル)。`-i :5555` — 5555 番ポートを使うネットワーク接続だけ。

課題: 5555 番ポートを占有している **プロセス名** を `~/work/port-owner.txt` に保存してください。

プロセス名を取り出して保存:

```
sudo ss -ltnp sport = :5555 | grep -o 'python3' | head -1 > ~/work/port-owner.txt
```

- `grep -o` — 行全体ではなく **一致した部分だけ** を出力する。`users:(("python3",pid=…))` から名前だけを取り出す。
- `head -1` で 1 つだけ残して `>` で保存。

保存内容の確認:

```
cat ~/work/port-owner.txt
```

- `cat <ファイル>` — ファイルの内容をそのまま表示する。

この python3 の正体が気になるなら、PID で /proc をもう一度探ってみましょう — ステップ 1 で学んだ方法そのままです。保存したら **[チェック]** してください。
